# winsnap：Alt+滚轮缩放动画 —— 失败经验记录

> 日期：2026-08-06　·　结论：**不要给窗口缩放做动画，滚轮缩放保持瞬缩。**

## 结论（告诫后人）

在 winsnap 里**不要**给 Alt+滚轮缩放做任何动画效果。滚轮缩放必须**瞬缩**（`on_scroll` 直接调 `cfg::scale_window`）。

若未来想改善缩放手感，方向是**减少 resize 次数（瞬移）**，而不是平滑化。

## 根因

窗口 resize 动画的成本由**目标窗口自身的重绘速度**决定：每次 `SetWindowPos` 都会向目标窗口发送 `WM_WINDOWPOSCHANGED`，目标应用必须重新布局并重绘整个客户区。动画线程从外部只能不断发出 resize 请求，**无法加速目标重绘**，因此：

- 重绘轻的窗口（记事本等）动画流畅；
- 重绘重的窗口（文件资源管理器、浏览器等）每一帧都卡顿。

这是物理限制，调参（步长、帧间隔、定时器精度）只能缓解表象，无法消除。

## 失败历程（所有方案均已回退）

依次尝试了 5 类方案，全部失败：

| # | 方案 | 结果 |
|---|------|------|
| 1 | 每格滚轮重启动画线程 | 快速滚动时线程反复启停，一顿一顿 |
| 2 | 追赶模式（单线程指数逼近，目标持续累加） | 轻窗口尚可，重窗口（资源管理器）仍卡 |
| 3 | 异步 SetWindowPos（`SWP_ASYNCWINDOWPOS`） | 异步请求在目标线程积压，反而更卡 |
| 4 | 快照分层预览（隐藏真实窗口 + PrintWindow 抓图 + `UpdateLayeredWindow` 开图层） | 画面效果差；**且隐藏目标窗口后动画一旦中断未恢复，窗口会"坏死"无法控制**，破坏性副作用不可接受 |
| 5 | 纯调参（加大步长 / 帧间隔 / `timeBeginPeriod(1)` / 单帧移动上限 / 抑制滚轮日志） | 越调越差，用户决定放弃动画 |

## 最终恢复状态

- 提交 `f5d8c76`：Alt+滚轮缩放恢复为**瞬缩**，移除全部缩放动画代码（`SCALE_TARGET`、`update_scale_target`、`scale_anim_loop` 等，净删 100+ 行）。
- **移动动画保留**：Alt+数字定位 / Alt+方向键贴边 仍为丝滑动画（ease-out cubic、200~400ms、追赶式单线程），由托盘菜单「开启动画」开关控制。
- 保留的无害优化：
  - `timeBeginPeriod(1)`：提高系统定时器精度，拖拽/移动动画帧间隔更均匀；
  - 连续滚轮日志抑制（250ms 间隔）：避免控制台 I/O 拖慢 rdev 事件线程。

## 相关代码位置

- 缩放入口：`src/main.rs` → `on_scroll`（瞬缩，无动画）
- 移动动画：`src/main.rs` → `animated_move` / `animate_window_to`
- 缩放逻辑：`src/config.rs` → `scale_window` / `scale_window_target`
